# BIRD-Benchmark-for-NL2SQL++
This Repository adapts mini_bird, a subset of the NL to SQL bird benchmark, for NL to SQL++ conversion

## Usecase

This project aims to benchmark the performance of Couchbase iQ on the BIRD Datatset. Each natural language question and the corresponding evidence statement are sent to iQ vis cbq, utilizing the "USING AI" command. The structure of each command looks something like this

` USING AI WITH {"keyspaces":[],"execute":true/false} <the prompt added as per requirement>; Q:<nl question> H:<evidence> `

At this point iQ calls to the OpenAI GPT-4o model. These commands are executed and an object containing the "generated_statement" is returned. We then execute this generated statement and stores the results in a csv file.

## Setup

We evaluate the performance of iQ by comparing the end product output (i.e. the CSV files) for the gold queries from the BIRD Benchmark and the sql++ queires generated by iQ. 

Firstly, we use `Scripts/sqlLiteToJson/tranform_sqlite_to_json.py` to convert sqlite files into json files. We then upload these to locally running CB server using `Scripts/loadDataToCB/batch_import_to_couchbase.py`. Once this is done we are done with CB setup. We can then run our USING AI queires on cbq as we want.

* `Scripts/testIQ` loads the data for each question from mini_dev_sqlite.json adds them to the prompt, makes a call to IQ, receives the generated SQL++ statement and stores the output as a csv file, along with the generated SQL++ statment.

* `Scripts/comparingResults/comparing_results.py` this scripts handles the comaprsion between csv files generated as a result of executing the sql++ queires given by iQ (test csv) and the csv files generated as a result of executing gold sql queires (gold csv). The comparisong logic is broken down in the following stages

Value Normalization: Before any comparison, all values in both dataframes are normalized to ensure consistent comparison. Strings are trimmed and converted to lowercase (" Hello " → "hello"), null representations are standardized (null/None/NaN/empty string/n/a all become None), and numbers are normalized (floats rounded to 6 decimals, whole floats like 42.0 converted to int 42). This prevents false mismatches caused by formatting differences between database systems - for example, ensuring "John" matches " john " and 3.14159265358979 matches 3.141593.

Type Detection: The script analyzes each column by sampling up to 100 values to determine its predominant data type, classifying columns as 'numeric' (≥80% of values are int/float or parseable as numbers), 'string' (≥80% are text), or 'mixed' (neither threshold met). This type awareness is crucial for preventing nonsensical column mappings - for example, it won't map a numeric "age" column to a text "name" column even if positional matching would suggest it. Type compatibility rules allow numeric↔numeric and string↔string mappings, while mixed columns can map to anything as a fallback.

Hybrid Column Mapping - Stage 1 (Fuzzy Matching): The first mapping attempt uses fuzzy string matching to find semantically similar column names, with a 70% similarity threshold. This catches cases like "user_id"↔"userId" (100% similar), "email_addr"↔"email" (90% similar), or "first_name"↔"fname" (78% similar), while rejecting weak matches like "total"↔"count" (43% similar). Type compatibility is enforced at this stage - only columns with matching types can be paired, even if their names are very similar. Columns successfully matched here are locked in and won't participate in the next stage.

Hybrid Column Mapping - Stage 2 (Positional Fallback): For columns that couldn't be matched by name similarity, the script falls back to positional matching - pairing unmapped columns by their left-to-right order. However, unlike naive positional matching, this stage still enforces type compatibility: the first unmapped gold column will only match the first unmapped test column if their data types are compatible. If types don't match, the script tries the next unmapped test column. This prevents mapping "age" (numeric, position 3) to "city" (string, position 3) just because they happen to be in the same position.

DataFrame Alignment: Once the column mapping is established (combining Stage 1 and Stage 2 matches), the test dataframe is transformed to align with the gold schema. Test columns are renamed according to the mapping (e.g., "userId" becomes "user_id"), unmapped test columns are dropped (extra columns are acceptable and simply ignored), only columns that exist in the gold schema are retained, and finally columns are reordered to match the gold column order exactly. This ensures that when rows are compared, the values line up correctly.

Row Comparison: The aligned dataframes are compared at the row level by converting each row into a tuple of values and creating sets of these row-tuples for both gold and test. The comparison identifies missing rows (in gold but not in test) and extra rows (in test but not in gold). The success criteria is strict: the test must have EXACTLY the same rows as gold - zero missing rows AND zero extra rows. Even if the test contains all the gold rows, having additional rows causes failure because it indicates incorrect query logic (wrong WHERE clause, JOIN, or aggregation). If the tuple-based comparison fails but row counts match, a fallback method treats each row as a frozenset of values (order-independent), which can catch cases where column mapping wasn't perfect but the data is present.

Success Classification: A comparison is marked as "success" if the test has exactly the same rows as gold (no missing, no extra), regardless of column name or order differences since those are handled by mapping. An "exact match" is a success where the test also has the same number of columns as gold (no extra columns in test schema). A "failure" occurs when there are missing rows, extra rows, or when column mapping completely failed. Notably, even one extra row causes failure - the validation is strict on row content but flexible on schema differences.

## Pipeline

Then we also take a multipass approach to this. In `Scripts/pipeline.py`, we first execute the logic from `testIQ.py` then carry out the compariosn logic from `compare_results.py` and from this we stores the queires that failed in this initial run. We then try to generate sql++ just for these failed queires and again carry out comparison. We then take number of successfully generated queires from both of these runs as our final number of successful queires. 
Therefore, the pipeline implments a two pass implmentation.
